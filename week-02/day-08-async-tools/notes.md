# Day 8 学习笔记 — 多工具并发调用(异步实测)

> 把 Day 4 的同步 ReAct loop 升级成异步并发版,实测**只省了 0.8s**(加速 1.07x)。
> 数据"不惊艳"但**非常诚实** — 戳破了"异步必快"的迷思。

---

## 📊 今日实测数据(工具延迟 0.5s)

| 指标 | 同步串行 | 异步并发 | 差异 |
|------|:---:|:---:|:---:|
| **耗时(秒)** | **12.08** | **11.28** | -0.80 |
| 迭代轮数 | 3 | 3 | 同 |
| 工具调用次数 | 5 | 5 | 同 |
| Token 总消耗 | 2495 | 2555 | +60 |
| **加速比** | — | **1.07x** | — |

**ReAct loop 流程**:
```
Round 1: search_products × 1                    (撒网)
Round 2: get_product_info × 4(异步并发)         (聚焦)
Round 3: 没工具,输出最终推荐                     (收官)
```

---

## 🔍 数据拆解(为什么只加速 1.07x?)

### 时间构成

```
LLM 时间(几乎不变):
  同步:12.08 - 工具(5 × 0.5 = 2.5s) = ~9.58s
  异步:11.28 - 工具(0.5 + 0.5 = 1.0s)= ~10.28s
  → LLM ~10s,占总时间 85-91%

工具时间(异步省了):
  同步:5 × 0.5 = 2.5s(串行)
  异步:max(每轮工具) × 轮数 = 0.5 + 0.5 = 1.0s(并发)
  → 节省 1.5s(理论)/ 0.8s(实测,asyncio 调度损耗)
```

**核心结论**:**LLM 时间是"恒定瓶颈",工具异步化只能砍 15%**。

---

## 💡 三个核心洞察(博客 #2 主线)

### 洞察 1:**工具延迟 vs 异步收益的关系**

| 工具延迟 | 异步加速比 | 工具时间占比 | 适用建议 |
|:---:|:---:|:---:|------|
| 0s(本地函数) | **1.0x** | 0% | ❌ 别用,asyncio 开销 > 收益 |
| 0.1s | 1.05x | 5% | ❌ 不值 |
| **0.5s** | **1.07x** | 15% | ⚠️ 边际(你刚跑的)|
| 1.0s | ~1.20x | 30% | 🟡 可选 |
| 2.0s | ~1.43x | 50% | ✅ 推荐(真实 API)|
| 5.0s | ~1.75x | 75% | ⭐ 必须(慢 API)|

**生产指导**:
- 本地函数(<10ms):**别用异步**
- 数据库查询(50-300ms):**可选**
- 真实 API(1-3s):**必须**
- 慢 API(5s+):**关键**

---

### 洞察 2:**LLM 调用本身才是大头**(W11 优化重点)

ReAct loop 的耗时构成:
```
4 轮 LLM × ~2.5s = 10s     ← 占 85%(无法砍,只能换更快的模型)
工具 IO ~2.5s              ← 占 15%(可异步并发)
```

**真正的优化方向**:
1. **LLM 调用层**:streaming(降 TTFT)/ 模型路由(快慢模型混用)/ Prompt Caching
2. **工具调用层**:异步并发 + 工具结果缓存
3. **整体设计**:减少不必要的 ReAct 轮数(Day 4 学的 prompt 设计)

> 💎 **金句**:**异步并发只能砍工具时间,砍不动 LLM 时间**。LLM 占 85% 时,工具异步化的天花板就是 15%。

---

### 洞察 3:Token 略有差异(2495 vs 2555,+60 output)

两次跑的 token 不完全一样:
- 同步:input=1959, output=536
- 异步:input=1971, output=584

**为什么?**
- 模型每次响应有微小差异(temp=0 也不是 100% deterministic)
- system_prompt 固定,但模型生成的文字略有不同
- LLM 的"几乎确定但不完全确定"是工程化的隐形坑

> 💎 **生产警告**:做 SDK 的"等价性测试"时,**不能用 token 数严格对齐**,要用 schema / 语义对齐。
